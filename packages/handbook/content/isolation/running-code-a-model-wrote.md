## The model

Two facts, and neither of them is about the model being wrong.

**Generated code is untrusted input.** OWASP files this as improper output handling, "insufficient
validation, sanitization, and handling of the outputs generated by large language models before they
are passed downstream to other components and systems", and names the exact sink: "LLM output is
entered directly into a system shell or similar function such as `exec` or `eval`, resulting in
remote code execution." Its guidance is one sentence long and settles the usual objection: "Treat the
model as any other user, adopting a zero-trust approach."

The objection is worth answering properly, because it feels strong. You wrote the prompt, so surely
the output is yours. It is not, because the output was shaped by whatever the model read on the way
there: a page a tool fetched, an uploaded document, an inbound email, a row somebody else wrote. That
is the same surface [the tool-call loop](../ai-engineering/the-tool-call-loop.md) already has to
survive, arriving at a more dangerous place.

**Code runs with the privileges of whatever runs it.** That is
[the process page](./what-a-process-gives-you.md) and there is nothing AI-specific about it.
`exec` in your API handler is your API process: its environment, so the database URL and the provider
key, its filesystem, its network, its identity to every service that trusts it.

So the question is never "how do I sanitise this code". There is no sanitiser for a Turing-complete
language, which is why the SQL answer here is not parameter binding: the model wrote the statement
and the literals together, and there is no value left to move onto a separate channel. The question is
where it runs and what is reachable from there, and there are exactly three things to take away.

**Credentials.** The runner holds none. Not scrubbed from the environment on the way in: a different
process, a different user, an environment built rather than inherited, so there is nothing to
scrub and no code path that forgets to.

**Egress.** No network by default, and an allowlist where the job genuinely needs one. This is the
subtraction people skip, and skipping it undoes the first one, because on a cloud instance the host's
credentials are available over plain HTTP to anything that can open a socket. AWS documents the
metadata service at `http://169.254.169.254/latest/meta-data/`, says the data "is not protected by
authentication or cryptographic methods" and that "potentially any software running on the instance,
can view its metadata", and lists `iam/security-credentials/{role-name}` as returning the temporary
credentials for the instance role. A sandbox with no secrets and a default network is a sandbox with
the host's secrets one request away.

**Time and memory.** A wall-clock budget and a memory cap, applied from outside, because a correct
program in an accidental loop is the failure you will meet long before a malicious one.

How strong the wall around those three needs to be is the rest of this section. A separate process
that has dropped everything is enough for code you wrote and want to be careful with; a container
gets you namespaces and cgroups over
[a kernel you still share](./what-a-container-is-made-of.md); a microVM is what
[the people running strangers' code](./where-a-virtual-machine-draws-the-line.md) settled on. What is
not on that ladder at all is `node:vm`, whose own documentation says it "is not a security mechanism".

## Worked example

The version that ships first, because it is four lines and it works:

```js
// The API process. It holds DATABASE_URL and the provider key.
async function runPython({ source }) {
  return execSync(`python3 -c ${JSON.stringify(source)}`).toString();
}
```

`JSON.stringify` is doing real work here and none of the work that matters: it stops the shell
splitting the argument, and the argument is a program. Adding "never read files or make network
requests" to the system prompt changes what tends to get generated and changes nothing about what
this line does with what it gets.

The same tool with the three subtractions made by the thing that starts the runner:

```js
async function runPython({ source }, session) {
  return runner.exec(source, {
    env: {}, // built, not inherited: nothing to scrub
    network: false, // link-local included, so no metadata service
    timeoutMs: 10_000,
    memoryMb: 512,
    scope: session.workspaceId, // the only data reachable is this session's
  });
}
```

Nothing about the source string changed. The API process keeps the secrets, and the code that could
read them is somewhere that has none.

This repo is the negative example, deliberately. `apps/server/src/grading/code-runner.ts` runs
submitted JavaScript in a `node:vm` context and is documented as a convenience rather than a
boundary, which is fine at the trust level it actually has: it runs code you typed, on your machine,
which is the trust level of `pnpm dev`. That single fact is also why self-hosting Hone was declined
rather than designed. A grader that executes submissions is a different proposition behind a public
interface, and the honest options were real sandboxing or no network interface. The decision was no
network interface, because the first one is a project rather than a deployment.

## Traps

**The system prompt says not to touch the filesystem.** A prompt is addressed to the thing writing
the code, and the thing running it never reads it. That holds even when nothing adversarial is
happening: a model that fully intended to comply still emits a library call that opens a file. An
instruction is a preference over what gets generated, and a control is something that fails closed.

**It runs in a `node:vm` context, so it cannot reach anything.** Node's own documentation refuses
this in one sentence, and the first page of this section has the three lines that walk out of a realm
built for exactly this purpose. The absent `process` global is not the boundary; the objects you had
to hand in are the way back.

**The sandbox has no credentials, and jobs are writing to the service's bucket.** They did not need
credentials, because the instance has them and the metadata endpoint hands them to anything on the
box. Egress is a separate subtraction from secrets and has to be made separately. IMDSv2 raises the
price rather than removing the endpoint: it wants a `PUT` for a token first, and AWS notes that with
a response hop limit of 1 a container counts as an extra hop and often cannot reach the service at
all. That is a mitigation, not a boundary.

**"It is our own prompt, so the code is ours."** The answer was shaped by tool results, and a tool
result carries content from pages, uploads and inbound mail. Nothing in the pipeline separates
instruction from data, which is why the control is what the runner can reach rather than what the
model was told.

**The generated SQL is going through the ORM, so it is parameterised.** A raw query the model wrote
end to end has no parameters: the values are in the string, put there by the same process that wrote
the syntax. What still works is bounding the session rather than the statement, which is a read-only
role granted the reporting views and a statement timeout.

**The runner is fine because it is a separate service.** Check what that service can reach. A runner
with a database connection, an internal network route, or an IAM role is the same problem one hop
further away, and the hop makes it harder to see. The test is what an attacker gets by owning the
runner completely, because generated code that escapes the language boundary owns the runner
completely.
