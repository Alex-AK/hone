## The model

Every remote call needs three answers, and they are separate decisions.

**How long do I wait?** A call without a deadline is not a call, it is a resource you have lent out
indefinitely. `fetch` has no timeout of its own, so a hung server holds your connection, your memory
and, at scale, your whole pool. Give it a deadline you picked from measured latency, not one that
sounds round.

**Can I send it again?** RFC 9110 answers this by method. Safe methods are "intended only for
retrieving information and should not change the state of the server": GET, HEAD, OPTIONS, TRACE.
Idempotent methods are the ones where "an identical request can be made one or more times with the
same intended effect as making that request just once": the safe ones plus PUT and DELETE. The rule
that follows is explicit. GET, HEAD, PUT and DELETE "can be retried automatically upon connection
failure or a 5xx response", while "a client SHOULD NOT automatically retry requests with unsafe
methods unless it has some means of knowing that the request semantics are idempotent". POST is the
method that fails that test, and it is the method that moves money.

The reason this is sharp rather than pedantic: a timeout tells you nothing about what the server
did. The answer was lost, not the request. A POST that timed out may have been fully processed, and
nothing in what came back distinguishes that from a POST that never arrived.

**How long before I try again?** Not immediately, and not on a fixed schedule. Exponential backoff
spaces the attempts out: clients "multiply their backoff by a constant after each attempt, up to
some maximum value". On its own that still fails at scale, because every client that failed in the
same second retries in the same second and the recovering server gets hit by the whole crowd at
once. Jitter is the fix, and full jitter is the version worth memorising: sleep for
`random(0, min(cap, base * 2 ** attempt))`. AWS's simulation of it found both the number of calls
and the time to completion improved over plain backoff.

When the server tells you how long to wait, that beats your formula. `Retry-After` comes back with
429 and 503 and carries either a delay in seconds or an HTTP date.

The last piece is what makes an unsafe request retryable at all: an idempotency key. It is "a unique
value generated by the client which the resource uses to recognize subsequent retries of the same
request". The server stores the key with the result, and on a repeat it "SHOULD respond with the
result of the previously completed operation, success or an error" rather than doing the work twice.
If the retry arrives while the first is still running, the draft says to answer 409.

## Worked example

A retry that respects all three decisions, and refuses to guess about the fourth:

```js
const RETRYABLE = new Set([429, 502, 503, 504]);

async function call(url, options = {}, { attempts = 4, base = 200, cap = 5000 } = {}) {
  for (let attempt = 0; ; attempt++) {
    const response = await fetch(url, { ...options, signal: AbortSignal.timeout(3000) });
    if (response.ok || !RETRYABLE.has(response.status)) return response;
    if (attempt >= attempts - 1) return response;

    // The server's own answer wins over the formula.
    const after = Number(response.headers.get('retry-after'));
    const wait =
      Number.isFinite(after) && after > 0
        ? after * 1000
        : Math.random() * Math.min(cap, base * 2 ** attempt);

    await new Promise((resolve) => setTimeout(resolve, wait));
  }
}
```

The loop retries only statuses the server chose to send, which means it retries a request that
definitely did nothing. A thrown `TimeoutError` is the ambiguous case and deliberately not caught
here: retry it for a GET, and for a POST only if it carries a key.

```js
// One key per intent, generated before the first attempt.
const key = crypto.randomUUID();

await call('/charges', {
  method: 'POST',
  headers: { 'Idempotency-Key': key, 'Content-Type': 'application/json' },
  body: JSON.stringify(charge),
});
```

Where that key is created is the whole trick. Generate it once for the thing the user asked for, not
once per attempt, or every retry looks like a new charge.

## Traps

**The customer was charged twice, and both charges look legitimate.** The POST timed out, the client
retried, and the first request had succeeded all along. Neither side did anything wrong: the request
arrived and the response was lost. An idempotency key, minted once per intent and stored server-side
with its result, is the only thing that closes it.

**Everything recovered at the same second, then fell over again.** Backoff without jitter. The
clients failed together, so their doubling schedules stayed in lockstep and they arrived together on
every attempt. Sleeping a random duration up to the backoff, rather than the backoff itself, breaks
the convoy.

**A slow dependency turned into an outage.** Three retries at the HTTP client, inside three retries
at the service layer, inside a caller that also retries, is twenty-seven requests for one user
action, aimed at something already struggling. Retry at one layer, cap the attempts, and put the
deadline on the whole operation rather than on each attempt.

**A 429 that got answered with an immediate retry.** The server said how long to wait and the client
did not read it. `Retry-After` is on the response for exactly this, in seconds or as a date, and
ignoring it is how a rate limit turns into a ban.
